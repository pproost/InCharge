# InCharge ↔ HealthCoach contract

**Contract version: 1**

This document is the single source of truth for the data InCharge exchanges with the HealthCoach server. The InCharge model *is* the contract: HealthCoach copies these shapes and does not invent its own session structure. Any change here is a contract change.

## General rules

- **Transport:** HTTPS, JSON, UTF-8. Property names are `camelCase`.
- **Authentication:** every request carries `Authorization: Bearer <device-token>`. There is one token for the one device.
- **Version:** every request and response body carries `"contractVersion": 1`.
  - Adding an optional field does **not** bump the version. Receivers ignore fields they don't know.
  - Removing, renaming or changing the meaning of a field **does** bump it.
  - The server answers `400` to a version it doesn't support.
- **Ids:** opaque strings. InCharge generates them as 32 lowercase hex characters (a GUID without dashes). Plan ids are generated by the server and treated as opaque by the app.
- **Timestamps:** ISO 8601 **with offset**, e.g. `2026-11-23T18:05:12+01:00`.
  - InCharge sends local time with the device's offset at that moment. The server stores UTC and shows Europe/Brussels.
  - Entries logged before contract v1 were stored without an offset. InCharge converts them with the Europe/Brussels offset that applied at that instant, so daylight saving time is correct.
- **Dates without time** (a plan's day): `yyyy-MM-dd`, meaning that calendar day in Europe/Brussels.
- **Durations:** whole seconds, integers.
- **Offline-first:** the app syncs whenever it can. The server must accept late, out-of-order and repeated uploads (see *Idempotency*).

## Shared types

### `ActivityType`

The activity type travels **by name**, never by the app's local id.

```json
{ "name": "Cycling", "icon": "🚴" }
```

| Field | Type | Notes |
|---|---|---|
| `name` | string | Matched case-insensitively. Agreed names for the coach: `Cycling`, `Rowing`. |
| `icon` | string, optional | One emoji. Purely cosmetic. |

- **Importing a plan:** InCharge reuses an existing type with the same name (case-insensitive) or creates it.
- **Renaming a type in the app:** every logged session with that type is queued for upload again, so the server ends up with the new name.

### `SessionStructure`

The structure of an interval session: an optional warm-up, groups of blocks that repeat, and an optional cool-down. Basic and Advanced sessions both use it.

```json
{
  "warmupSeconds": 300,
  "groups": [
    {
      "repeat": 4,
      "blocks": [
        { "kind": "move", "seconds": 90, "label": "Hard" },
        { "kind": "rest", "seconds": 60, "label": "Easy spin" }
      ]
    }
  ],
  "cooldownSeconds": 300
}
```

| Field | Type | Notes |
|---|---|---|
| `warmupSeconds` | int, optional | Omitted or `null` = no warm-up. Otherwise ≥ 1. |
| `groups` | array of `Group` | At least one group. |
| `cooldownSeconds` | int, optional | Omitted or `null` = no cool-down. Otherwise ≥ 1. |

`Group`:

| Field | Type | Notes |
|---|---|---|
| `repeat` | int | ≥ 1. The group's blocks run this many times in a row. |
| `blocks` | array of `Block` | At least one block. |

`Block`:

| Field | Type | Notes |
|---|---|---|
| `kind` | `"move"` \| `"rest"` | |
| `seconds` | int | ≥ 1. |
| `label` | string, optional | Short intensity hint shown on the watch next to the phase, e.g. `Zone 2`, `Tempo`, `Hard`, `All-out`, `Easy spin`. **Max 20 characters**; InCharge trims longer labels. Omitted or `null` = no label. |

**How InCharge runs a structure** (needed to compute the planned duration):

1. The warm-up, if any.
2. Each group in order, its blocks repeated `repeat` times.
3. **Trailing rest rule:** if there is a cool-down and the last block of step 2 is a `rest`, that last rest is **skipped**. The cool-down replaces it.
4. The cool-down, if any.

A Basic Interval is expressed as one group: `{ "repeat": N, "blocks": [move, rest] }`, plus its warm-up and cool-down.

## Executed sessions (app → server)

### `POST /api/incharge/sessions`

Uploads a batch of executed sessions from the app's outbox. It is also used once for the existing history.

Request:

```json
{
  "contractVersion": 1,
  "sessions": [ /* ExecutedSession or Tombstone */ ]
}
```

`ExecutedSession`:

```json
{
  "id": "3f9c2e0b8a6d4c1e9b7a5d3c1e0f2a4b",
  "updatedAt": "2026-11-23T18:52:40+01:00",
  "name": "Pyramid 30",
  "source": "coach",
  "sessionId": "a1b2c3d4e5f60718293a4b5c6d7e8f90",
  "planId": "plan-2026-W48-2",
  "type": { "name": "Cycling", "icon": "🚴" },
  "startedAt": "2026-11-23T18:05:12+01:00",
  "completedAt": "2026-11-23T18:41:03+01:00",
  "finishedEarly": true,
  "structure": { /* SessionStructure, as planned */ },
  "totals": {
    "activeSeconds": 2091,
    "warmupSeconds": 300,
    "moveSeconds": 1080,
    "restSeconds": 600,
    "cooldownSeconds": 111,
    "moveBlocks": 12
  },
  "pauses": { "count": 1, "seconds": 64 }
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | string | The log entry id. Key for idempotency. |
| `updatedAt` | timestamp | Time of the last local change to this entry (creation, type change, deletion). Used to resolve out-of-order uploads. |
| `name` | string | Session name as shown in the app (`Basic Interval` or the Advanced session name). |
| `source` | `"basic"` \| `"advanced"` \| `"coach"` | `coach` = an Advanced session imported from a plan. |
| `sessionId` | string, optional | Id of the Advanced session that was run. `null` for Basic. |
| `planId` | string, optional | Set when the run came from an imported plan. Links planned and executed. |
| `type` | `ActivityType`, optional | `null` when no type was picked. |
| `startedAt` | timestamp | When the run started. The server matches this with the Google Health workout (±5 minutes). |
| `completedAt` | timestamp | When it completed or was finished early. |
| `finishedEarly` | bool | `true` when Peter used "Finish now" before the end. |
| `structure` | `SessionStructure`, optional | The structure **as planned when the run started** (including local edits to a coach plan). `null` for entries logged before contract v1. |
| `totals` | object | What was **actually done**, in seconds. For an early finish this includes the partial last phase. `activeSeconds` is the sum of the four phase totals and excludes pauses. `moveBlocks` counts started move blocks. |
| `pauses` | object | `count` and total paused `seconds`. |

`Tombstone`, sent when Peter deletes a logged session in the app:

```json
{ "id": "3f9c2e0b8a6d4c1e9b7a5d3c1e0f2a4b", "updatedAt": "2026-11-24T08:10:00+01:00", "deleted": true }
```

Response `200`:

```json
{ "contractVersion": 1, "accepted": ["3f9c2e0b8a6d4c1e9b7a5d3c1e0f2a4b"] }
```

- InCharge removes every id in `accepted` from its outbox and retries the rest later.
- `401`: wrong or missing token. Sync stops and Settings shows the error; nothing is retried until the settings change.
- `400`: invalid payload or unsupported `contractVersion`. Not retried automatically.
- `5xx` or no connection: everything stays in the outbox and is retried on the next sync.

**Idempotency:** the server upserts on `id`.

- An item whose `updatedAt` is older than what the server already has for that id is accepted but ignored.
- A tombstone deletes the session, or marks it deleted.
- A later upsert with an older `updatedAt` does not bring a deleted session back.
- Sending the same batch twice is always safe.

## Planned sessions (server → app)

### `GET /api/incharge/plans?since=<cursor>`

Returns plans that are new or changed since the cursor. The first call omits `since` and gets everything that is not yet `Delivered`.

Response `200`:

```json
{
  "contractVersion": 1,
  "cursor": "2026-11-23T17:00:00.0000000Z",
  "plans": [
    {
      "planId": "plan-2026-W48-2",
      "plannedDate": "2026-11-25",
      "name": "Pyramid 30",
      "note": "Short and sharp after an easy Monday; keep the top blocks honest.",
      "type": { "name": "Rowing", "icon": "🚣" },
      "structure": { /* SessionStructure */ }
    }
  ]
}
```

| Field | Type | Notes |
|---|---|---|
| `cursor` | string | **Opaque.** The app stores it and sends it back as `since` next time. It comes from the server's clock, so the phone's clock doesn't matter. |
| `planId` | string | Unique, generated by the server. |
| `plannedDate` | date | The day the session is planned for. |
| `name` | string | Shown as the session name. |
| `note` | string, optional | Claude's short explanation of why this session. Shown in the session details. |
| `type` | `ActivityType` | Resolved by name on import. |
| `structure` | `SessionStructure` | |

**The app wins.** InCharge keeps the list of every `planId` it ever imported.

- A plan whose `planId` is already on that list is ignored: it is never overwritten, and never brought back if Peter deleted it locally.
- Changes the server makes to an already delivered plan therefore don't reach the app. Plan a new session instead.

On import, a plan becomes an Advanced session:

- `source = coach`, with `planId`, `plannedDate` and `note`.
- The type is resolved by name.
- The duration unit is minutes when every duration is a whole number of minutes, seconds otherwise.

### `POST /api/incharge/plans/{planId}/delivered`

Confirms that the plan is in the app. It moves the plan from `Proposed` to `Delivered`.

Request:

```json
{ "contractVersion": 1, "deliveredAt": "2026-11-23T18:00:02+01:00" }
```

Response `204`. Idempotent: confirming twice is fine, and so is confirming an unknown plan (also `204`).

## Plan status (server side, for reference)

`Proposed` → `Delivered` → `Done` or `Skipped`.

- `Delivered`: the app has confirmed it.
- `Done`: an executed session with this `planId` exists.
- `Skipped`: `plannedDate` plus 1 day has passed without a run.
